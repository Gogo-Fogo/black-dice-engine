# Shared runtime contracts

`@black-dice-engine/contracts` is the first shared npm workspace with production consumers: the dashboard, companion, game server, audio service and Comfy router. It exports Party state/view/choice/stage/action types, local session identity, command metadata/key types and pure runtime guards. The package has no dependency, I/O, framework, Node or browser platform API. Its TypeScript config includes only ES2022 libraries and no ambient Node types.

`src/index.ts` owns the Party/player primitives; `src/ttrpg.ts` owns host wire types, `src/ttrpg-validation.ts` their runtime guards and `src/ttrpg-responses.ts` the consumed host response envelopes. The index is the emitted public entrypoint. `npm run build --workspace packages/contracts` emits native ESM and generated declarations in ignored `dist/`. Consumers use that emitted entrypoint, never a server module or another app's type file. Root workspace ordering and the Party launcher build contracts first; root lint/test and app/server development shortcuts also build it before consumers. Direct workspace commands require this prerequisite build.

The manifests/lockfile declare the local workspace relationship. Existing installed dependencies predate this package, so source consumers use explicit repository-relative `packages/contracts/dist/index.js` imports. These resolve without creating a workspace link or running an installation. The manifest's exported entrypoint is the same file; a later separately authorized install can create the normal named workspace link. No third-party dependency or registry resolution was added. Relative paths have the same depth from service `src/` and `dist/`, so emitted NodeNext imports remain valid.

Guards validate shape/bounds and selected cross-field constraints (unique roster/participants, known participant choices). They do not authenticate an actor, authorize a command, apply game rules, check stored score arithmetic or decide visibility. The server still owns those behaviors. `PartyState` contains unrevealed choices and must pass through `projectParty` before delivery. A successful `isPartySnapshot` call is not a privacy guarantee for arbitrary values or unknown extra fields.

The server uses `isPartyState` before restoring/projecting saved data. Browser receipt/live-update paths use `isPartySnapshot`. Bad nested state fails with a host error rather than a partially projected game. Strict shared request ID/metadata guards retain separate authenticated actor/revision/stage checks in command services.

Existing `../shared-schemas` JSON files and `$id` values remain stable. Targeted tests compare Party protocol enums/request IDs with those schemas; this is not a full JSON Schema validator or generator. Full source/schema unification and remaining TTRPG/AI/media consumer adoption remain open ROOT-03/04 work. No validator/generator was installed.

If an extracted contract breaks compatibility, restore the former implementation/callers from version control and rebuild affected workspaces. No database schema, record migration, resource location or credential format changed. Do not edit stored data to work around a contract failure; recover a separately rehearsed demo backup if needed.

## TTRPG host contracts

The dashboard compatibility module reexports the shared host types; the game server imports the same definitions instead of maintaining copies. Server-produced `character_created`/`initiative_set` event kinds and live local/director adapter variants are retained. `StateEventRequest` preserves the producer's optional request ID for internal proposals, while `StateEventCommand` requires it for submitted commands; `StateEventDraft` derives the draft union without that ID. Audio library/playback definitions also have one source, consumed by the dashboard and audio service.

`SessionSnapshot` is the **host-only** shape, including protocol metadata, campaign context, approval/media/audio queues and full memory. It must not be sent to a player or public display. `PlayerSessionSnapshot` and server allowlist projections remain separate. The runtime-service's health report has a different shape from the game server's host `RuntimeStatus`; these are not interchangeable.

Host WebSocket dispatch now validates both halves of a connected frame before either callback runs. The owned host HTTP client validates bootstrap runtime/snapshot data, nested reports/logs and save/scene/memory confirmations. Guards check consumed nested fields and permit additive unknown properties; they are not authorization, privacy filters, timestamp parsers or game-rule validators. Opaque event payloads, media settings and log details remain object-valued by contract. The server still owns permission checks and projections before serialization.

`host-contracts.test.mjs` uses the real authenticated producer plus malformed nested variants. Table/media confirmations, scene packet/draft/queue reads, audio library/playback/cue responses and character creation now adopt shared guards through a small dashboard JSON boundary. Remaining adoption includes server-side optional service reads, persisted legacy record validation, typed server envelope construction and full JSON Schema/runtime parity. Exporting an AI/audio guard does not mean every consumer already calls it. No new validator or generator was installed and existing schema IDs/dialects were unchanged.

`sceneBeatKinds` is the shared beat enum for TypeScript, host validation and server packet admission. JSON Schema's existing beat enum now includes the already-produced `memory` kind; a targeted parity check keeps this enum aligned without changing the schema ID or dialect. A real producer test loads a generated packet and submits it through proposal/media/audio queues. This fixes the prior generated-packet self-rejection; it is not full schema generation/validation.

## Structured AI action suggestions

`src/ai-action.ts` maintains proposal types, accepted skill/ability and difficulty maps, bounds, runtime guards and the complete `aiActionProposalSchema` definition. The JSON artifact under shared-schemas is compared against that value by tests. The server accepts a single valid JSON object, optionally fenced, and returns 502 for malformed model output instead of treating an empty object or arbitrary prose as an actionable suggestion. Validation-failure diagnostics contain a generic reason, not the rejected raw output. This is not full diagnostic redaction or source-label enforcement.

The host validates proposal responses, converts them to the existing set-action contract (`type`, description, ability, DC), and checks a matching server confirmation after explicit application. Proposal generation itself does not mutate the current action, authoritative rolls, sheets or canon. Narration GET state and POST success use separate guards; the switch retains its last confirmed value on failure. UI bootstrap uses an epoch to avoid overwriting a later toggle and marks an unconfirmed initial setting unknown. Full session/revision-bound async cancellation and durable host retry queues remain open capability/engine work.

Verification uses only mocked completions inside isolated server children. It covers schema artifact parity, parser refusal, no action mutation on suggestions/rejection, explicit application and persisted restart, malformed/mismatched confirmations and static failure feedback. It does not mount the hook or exercise a live model or cloud provider. Rollback requires restoring the previous producer/client contract together and rebuilding; no stored-record migration is needed.

## Server audio-cue boundary

The game-server audio-cue owner validates the library and the returned playback envelope through shared guards. A successful HTTP status alone cannot mark a cue playing: the reply must confirm the selected track, playing status, volume and loop settings. Invalid/unavailable responses leave the queued state unchanged. Existing first matching tag selection and no-match 404 behavior remain.

One ten-second deadline covers library lookup and play confirmation. Concurrent requests for the same cue object share one operation; later explicit plays are permitted. Shutdown aborts owned operations, including settling callers when an injected adapter ignores abort. Late library completion cannot submit playback. A cue removed from the queue during the operation cannot be marked playing by the route. This is not durable playback idempotency, complete session/revision binding or proof of audible output; an already accepted remote play cannot be retracted by a local timeout.

## Comfy router job confirmations

`src/media-router.ts` owns router job types and guards for prepare/submit/status envelopes. The router producer imports the shared job type; the game server validates confirmations and matches job/workflow/type/prompt identity. The status envelope has `comfyStatus` and `job.status`, which must agree; it has no top-level `status`. Previously the game-server poller read that nonexistent field and never recognized terminal results. Non-success upstream bodies are excluded from submission errors.

The extracted game-server client keeps existing per-request deadlines (prepare ten seconds, submit fifteen, poll eight). Poll ownership prevents overlapping reads for the same live object and checks membership, running status, router ID and prompt ID before applying a terminal result. Start rejects an already-starting/running job and checks membership/status again before applying confirmation. This is not durable GPU submission deduplication, complete session/revision cancellation, provider-output validation or proof that a generated file exists. Router completion retains the existing metadata-recording behavior; asset publication/serving remain separate work. No schema ID, database layout or dependency installation changed.
