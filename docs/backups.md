# Online backups and validation

The game server owns backups of its open SQLite connection. `POST /api/backup` accepts an optional note of at most 200 characters and requires a GM/admin credential. It flushes current legacy state, then uses the installed SQLite online-backup API so committed WAL state is included. Concurrent requests share one snapshot. Configure `BDE_BACKUPS_DIR`; the default `_backups/` is ignored by Git. Prefer a private directory outside the repository for real sessions.

Each new timestamp/UUID directory contains `snapshot.db` and a version-1 `manifest.json`, published after snapshot/schema/integrity/hash checks succeed. The manifest records creation time, source path, schema version, byte size, SHA-256 and note. Public API metadata omits the source path. These files contain private session data and credentials/hashes: keep them private. No existing backup is overwritten or automatically deleted. Failed creation can leave an incomplete directory; it has no valid published manifest and is reported as invalid by listing.

`GET /api/backups` returns metadata for at most the newest 100 matching directories and an invalid count. Listing is not revalidation. `POST /api/backups/:backupId/validate` accepts only generated IDs, rejects symlinked records, checks size/hash, opens SQLite read-only, runs `quick_check`, and checks the application's migration history/schema. It does not migrate or replace the live database. Errors omit filesystem paths and native stack traces. Player/display credentials cannot use these endpoints. Shutdown waits for an already-running snapshot before closing SQLite.

Automatic snapshots default on (`BDE_AUTO_BACKUP=1`; use `0` to disable). The game-server process starts a snapshot after successfully binding its listener and creates another after draining requests and flushing final state during graceful shutdown. Startup backup failure leaves play available, writes a generic diagnostic and adds a host-only runtime warning. A successful manual backup clears that warning. Shutdown waits for snapshot publication before closing SQLite; a failed final snapshot makes shutdown exit unsuccessfully. Abrupt termination/power loss cannot produce a final snapshot. These are process-boundary backups, not a separate snapshot for every new-room command. No retention deletion runs automatically.

The launchers put backups beside their explicitly selected session data; direct starts retain the configured/default backup directory. The optional runtime service forwards operations and the caller's credential to the game server. It no longer copies database main files or schedules a second startup copy. Host-facing backup controls remain follow-up work. No live restore endpoint is provided. Restoring a real session requires separate review/authorization, stopping writers and preserving the current data; do not copy a snapshot over a running database.

`backups.test.mjs` uses disposable databases to prove live WAL inclusion, shared creation, checksum/future-schema refusal, manifest/path validation, persistence after restart and denied-player behavior. A restored copy is opened independently and compared while the live fixture retains newer data. An actual owned runtime/game-server pair verifies credential forwarding with outgoing requests restricted to its synthetic backup endpoints. No real database, backup, private path or campaign was opened.
