# Speech and automatic scene submission

`speech.ts` owns synthesis requests from the authenticated host route. Identical text in the same session/mode/round/stage/revision shares one job, with independent caller cancellation. It admits one active request and two waiting jobs; a 30-second deadline includes queue time and streamed response. Disconnecting the last caller, advancing scope or shutting down aborts owned work. Ignored transport cancellation cannot retain the logical queue or publish late results.

Speech accepts trimmed text of 1–4000 characters and checks HTTP status, WAV content type, declared/streamed byte bounds, RIFF/WAVE signature and RIFF length. Responses are limited to 8 MiB. These envelope checks do not decode audio or establish audible correctness. The current-scope in-memory cache holds at most eight items/16 MiB for five minutes; callers receive separate byte copies. Nothing is written to disk. Host responses use `Cache-Control: no-store`; provider errors become generic failures. The browser remains responsible for playback and disposal. Removed server self-requests previously discarded speech bytes without playing them.

`scene-images.ts` owns the workflow and transport formerly duplicated in scene/roll handlers. Both callers submit only after durable command success. One active/two waiting submissions have a ten-second deadline including queue/body processing, reject redirects, and accept only a bounded 16 KiB JSON acknowledgment with a valid prompt ID. Acknowledgment means submitted, not generated or approved. Same-scope identical prompts share pending and settled attempts; even failure/ambiguous acceptance cannot automatically retry. At most 64 attempts are remembered per current scope, then new submissions are refused until scope advancement. New scope cancels old active/queued work and clears old deduplication entries. Party mode or an empty endpoint makes zero submission calls. No outputs are automatically applied to game state.

Both owners are import-safe and receive transport, current scope and liveness from bootstrap. Committed broadcasts cancel stale jobs; shutdown disposes them. Deadlines release logical slots even when a provider ignores abort. This cannot remove already accepted ComfyUI work or prove physical GPU concurrency. Manual media-router preparation/submission/polling now uses the same lifecycle guarantees, described below. GPU scheduling, approved asset access and audible/device validation remain separate plan gates.

`speech.test.mjs` covers deduplication, admission order, cache copies/eviction/expiry, timeout, cancellation, malformed/oversized bodies and actual host/player HTTP behavior. Its WAV fixture checks only the transport envelope. `scene-images.test.mjs` covers FIFO admission, bounded attempt retention, ignored transport/body, all scope dimensions, shutdown, malformed acknowledgments and disabled paths. An actual isolated command test injects receipt failure and proves zero submissions on rollback, one on success and none on exact/restart replay. All provider replies are synthetic; no models, private outputs or live GPU services are accessed.


Manual router work shares one active/two waiting logical requests, including prepare/submit and status reads. A 25-second start or eight-second poll deadline covers queue time, headers and bounded 128 KiB JSON bodies. Starts share pending/settled attempts, reject changed input for a reused ID, retain at most 64 attempts per room/mode, and never automatically retry ambiguous acceptance. Polls share concurrent reads and may retry after failure. Scope changes, replaced/terminal jobs and shutdown settle/abort work; late preparation cannot proceed to submit. Ordinary rolls do not cancel a long-running manual job. Provider error bodies are excluded from errors and terminal callbacks.

The host route persists `settings.routerSubmissionAttemptedAt` and `routerSubmissionSessionId` before transport. Failed persistence sends nothing. Any attempted ID remains locked across failures/restarts; inspect ComfyUI and queue a new job deliberately to generate again. Known router IDs/status are persisted after acknowledgment. New-room jobs cannot adopt a prior room's marked submission. Legacy jobs without an origin retain their compatibility behavior pending broader persistence validation. These markers use the existing settings record; no schema migration is needed. The dashboard disables repeat generation and explains reconciliation. Eleven router tests cover this boundary, including actual failed admission, manual failure, room replacement and confirmed-ID restart recovery. CAP-05 is complete; direct access to the auxiliary router is not a physical GPU scheduling guarantee.
